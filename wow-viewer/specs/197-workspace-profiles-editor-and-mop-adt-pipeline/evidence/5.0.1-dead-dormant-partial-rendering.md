# WoW 5.0.1 Dead, Dormant, and Partially Implemented Rendering Paths

## Question

Which native 5.0.1 paths are demonstrably unfinished, unsupported,
developer-only, low-reachability, or retained as optional renderer
infrastructure, and which of them can explain ADT or terrain behavior?

This is a static evidence note for `Wow.exe` Mists of Pandaria 5.0.1.15464.
It follows the small-output pattern in the legacy
[`ghidra-definitive-guides.md`](../../../../gillijimproject_refactor/docs/ghidra-definitive-guides.md)
and is intended to feed the consolidated
[`wow-5.0.1-adt-wdt-definitive.md`](../../../docs/architecture/wow-5.0.1-adt-wdt-definitive.md).
No Ghidra program state or production code was changed.

## Evidence rules

The classifications below deliberately separate:

- **Partial:** a branch has an explicit unsupported/default path, incomplete
  switch coverage, or an apparent missing implementation.
- **Capability-gated:** the subsystem has supported and unsupported paths or
  checks hardware/resource state before use.
- **Optional:** a runtime setting or callback enables or disables the feature.
- **Lifecycle contract:** assertions describe ownership and teardown; they are
  not evidence that the subsystem is dead.
- **Low direct reachability:** no direct caller was recovered. This is only a
  candidate state because tables, callbacks, vtables, exports, and indirect
  calls are common in this client.
- **String-only lead:** a developer/debug/unfinished string was found, but its
  execution path was not mapped to a function.

The available dead-code result was not a completed reachability analysis in this
pass. No zero-direct-xref function is therefore called **proven dead** here.

## Decompiled evidence

### Liquid geometry factory: unfinished default branch

`FUN_00b7a230` selects a liquid geometry constructor from a format-like value:

```c
pcVar5 = (code *)0x0;

switch (param_2) {
case 7:
    pcVar5 = FUN_00b79390;
    break;
case 9:
    pcVar5 = FUN_00b78700;
    break;
case 10:
    pcVar5 = FUN_00b78cf0;
    break;
case 0xd:
    pcVar5 = FUN_00b78180;
    break;
default:
    FUN_00684120(..., "LiquidGeomFactories.cpp", 0x4c0,
                 "0 && \"Not implemented!\"", ...);
    break;
}

(*pcVar5)(*(undefined4 *)(param_1 + 0xc), param_1 + 0x28, &param_3);
```

The direct observations are:

- Recognized values are `7`, `9`, `10`, and `0xd`.
- The default branch does not assign a constructor before the apparent indirect
  call. The decompiler leaves the call target initialized to null.
- This is a genuine incomplete input domain, not an unrelated string in a data
  block.
- No direct caller was recovered for `FUN_00b7a230`; a factory table or callback
  can still invoke it.

This is the highest-value unfinished rendering finding because it is in native
liquid geometry construction, not UI or navigation.

### Water detail mode: explicit unsupported result

`FUN_00b27950` obtains a mode, asks a helper to apply it, and reports failure
without claiming the mode was accepted:

```c
uVar1 = FUN_00685ff0(param_3);
iVar2 = FUN_007dc400(uVar1);
if (iVar2 != 0) {
    FUN_00685df0(local_104, 0x100,
                 "Water detail changed to %d", uVar1);
    FUN_006ad560(local_104, 0);
    return 1;
}

FUN_006ad560("Unsupported water detail mode.", 0);
return 0;
```

This proves an explicit rejected-mode path. The absence of a direct caller does
not prove deadness: settings and Lua/CVar callbacks may be installed
indirectly.

### DepthCache: hardware/resource capability path

The binary retains these `DepthCache.cpp` strings:

```text
DepthCache is NOT supported!
DepthCache Resolve
DepthCache is supported!
```

The primary helper is `FUN_005c5300`, with direct callers at `FUN_005c5520` and
`FUN_005c5790`. One recovered assertion is:

```c
FUN_00684120(..., "DepthCache.cpp", 0x26, "!s_depthRT", ...);
```

The evidence supports an implemented resource subsystem that can be disabled
when the graphics device lacks the required depth render target. It is not dead
code. It remains open whether terrain submits work through this resource or
whether it serves another render pass.

### GBuffer: implemented, prepass and hardware gated

The GBuffer string family includes:

```text
GBuffer is NOT supported!
GBuffer - ShadowMask
GBuffer - Depth
GBuffer is supported!
Preparing to create GBuffer:
Prepass Mode (0 - no prepass, 1 - GBuffer, 2 - pure prepass)
```

The recovered function family is:

```text
FUN_005c74a0  -> FUN_005c7900, FUN_005c7a00
FUN_005c7820  -> FUN_005c7940
FUN_005c7940 -> FUN_005c5ff0, FUN_007dc1c0, FUN_007dc400, FUN_00cc8900
```

Observed assertions include:

```c
assert(!s_depthRT);
assert(!s_normalRT);
assert(s_gbufferFB);
```

The correct classification is **implemented optional infrastructure**:

- `Prepass Mode` exposes no-prepass, GBuffer, and pure-prepass modes.
- The negative support message proves a device-dependent rejection path.
- The lifecycle functions carry render-target and refcount invariants.
- This evidence does not show that GBuffer is the default 5.0.1 terrain path.

### Texture atlas and batching: live feature toggles

`FUN_004019e0` accepts a setting value, rejects values above `3`, and clears the
atlas bit when device/context state is incompatible:

```c
if (3 < uVar1)
    return 0;

if ((uVar1 & 1) != 0 && device_state_is_incompatible()) {
    uVar1 &= ~1;
    FUN_006ad560("Texture atlas disabled.", 0);
}

FUN_005a8940(uVar1 & 1);
DAT_00f4b218 = (uVar1 >> 1) & 1;
return 1;
```

The helper predicates are not renamed here, but the state machine is clear: the
atlas is optional and may be forcibly disabled.

The batching callbacks are similarly explicit:

```c
// FUN_00401ab0
if (enabled) {
    FUN_00550280(current_flags | 0x10);
    FUN_006ad560("Doodad batching enabled.", 0);
} else {
    FUN_00550280(current_flags & ~0x10);
    FUN_006ad560("Doodad batching disabled.", 0);
}
return 1;

// FUN_00401b10 uses 0x40 and the equivalent particle messages.
```

These are configuration surfaces with enable and disable behavior, not dead
renderer branches.

### `CSimpleEditBox`: explicit unfinished branch

`FUN_004b16d0` references `CSimpleEditBox.cpp` and contains:

```c
if ((*(byte *)(param_1 + 0x204) & 2) != 0) {
    FUN_00684120(..., "CSimpleEditBox.cpp", 0x720,
                 "!\"FIXME: Not yet implemented\"", ...);
    return;
}
```

This is confirmed partial UI behavior. The controlling flag is bit `0x2` at
object offset `0x204`; the normal edit-box operation is skipped. It is unrelated
to ADT loading or terrain rendering, but it is a useful control example of an
explicit FIXME plus an early return.

### Terrain cleanup: ownership contracts

`FUN_005c55140` (`MapArea.h`) asserts that diffuse and height textures have been
released and, when the applicable flag permits it, that the area refcount is
zero:

```c
assert(m_diffuseTexture == 0);
assert(m_heightTexture == 0);
assert(m_refCount == 0);
```

`FUN_00bac5b0` (`MapRenderChunkState.h`) asserts:

```c
assert(m_refCount == 0);
assert(m_diffuseTexture[i] == 0);
assert(m_heightTexture[i] == 0);
assert(m_envTexture == 0);
assert(m_renderLink.IsLinked() == 0);
```

The loop over four texture slots and the render-list unlink are especially
useful for split-ADT work. A tile that parses correctly but fails to release
height/diffuse state can resemble a file-family or residency bug.

These leads belong in the inventory, but require xrefs or registration evidence
before promotion to dead-code findings.

## Low-reachability inventory and interpretation

The static search produced **2,184 functions with zero direct xrefs**, mostly
unnamed `FUN_*` routines. This is a candidate pool, not a dead-code count.

Real client functions can have no direct caller because of:

- vtable slots and virtual dispatch;
- graphics or resource callback tables;
- Lua/CVar command registration;
- script/event registration;
- exports or plugin-style entry points;
- jump tables and computed dispatch;
- function pointers stored in factories such as the liquid geometry path.

The correct follow-up for a zero-xref candidate is to inspect data xrefs to the
function, registration records, vtable layout, import/export relations, and
indirect-call sites. Only after those are negative should it be called a dead
code candidate, and even then the confidence remains static.

## Definitive answer

- `FUN_00b7a230` is the clearest native partial implementation found: four
  supported switch values are visible, while the default branch asserts
  `Not implemented!` and leaves the apparent call target unset.
- DepthCache and GBuffer are not dead. They are implemented, connected
  subsystems with explicit capability rejection paths and lifecycle assertions.
- Texture atlas, doodad batching, particle batching, and water-detail handling
  are optional/configuration paths with explicit disable or unsupported results.
- The `CSimpleEditBox` FIXME branch is confirmed unfinished UI behavior, not a
  terrain defect.
- Terrain cleanup assertions are resource ownership contracts and should inform
  viewer diagnostics for split-ADT textures and height resources.
- No function in this note is classified as **proven dead**. Zero direct xrefs
  remain low-reachability candidates until indirect dispatch is ruled out.

## Confidence

- **High:** liquid factory switch/default, UI FIXME early return, batching bit
  operations, and terrain cleanup assertions; these are direct decompiler
  observations.
- **Medium:** DepthCache/GBuffer as optional renderer infrastructure and the
  likely callback nature of no-direct-caller settings; callers and strings
  establish the paths, but terrain ownership is incomplete.
- **Low:** any claim that a zero-xref function is dead, that a developer archive
  is mounted in ordinary play, or that an unsupported capability path is never
  taken on a particular machine.
