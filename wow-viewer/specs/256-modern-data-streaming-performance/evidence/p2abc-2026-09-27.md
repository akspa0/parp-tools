## Behaviour notes

- P2a: identical pixels, wrap modes and resolution order. A shared texture keeps the sampling settings of its
  first upload (native M2s never re-applied sampling after upload before either).
- P2b: pixels identical; a section whose texture is still streaming is **not drawn** until it resolves (textures
  can appear a few frames after a model is placed); a section with no loadable texture draws untextured, as before.
- P2c: level 0 matches the library decode (0 bytes different in the earlier R-39 synthetic check, incl. the DXT1
  transparent mode); lower mips come from the file instead of `GenerateMipmap` — the operator-approved change.

## Correction 2026-09-27 — P2b regression fixed

Operator capture after `a7808ff`: 2 FPS, world CPU 530 ms, model loading 427 ms in the frame, **predicted M2 load
cost 659.8 ms** (was 64.5 ms), 103 GiB allocated. Cause (code, found from the capture): P2b's candidate builder
resolved replaceable fallback slots 11 and 1 for **every section up front**; `ResolveReplaceableTexture` probes up
to ~135 naming-convention paths through `IDataSource.ReadFile` and then scans every `.blp` in the data source.
The synchronous loader only resolves a fallback slot after every candidate (and the previous slot) failed.
Fix: fallback slots are streamed as stages 1 (slot 11) and 2 (slot 1), each resolved only after the previous stage
failed — the synchronous order and laziness. Runtime Stats' load-phase lines now wrap so no value is cut off.
Build 0 errors, same 26 failures. Remaining cost to watch: sections whose own textures fail still pay the
fallback resolution (as before P2), now on the render thread when the failure result arrives.
