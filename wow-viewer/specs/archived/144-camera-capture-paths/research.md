# Research: Camera Capture Paths

- Existing capture automation is implemented in `ViewerApp_CaptureAutomation.cs`: shot-point JSON, still capture queue, ffmpeg video recording, and startup capture arguments already exist.
- The existing UI exposes that route only through `Tools > Utilities > Capture`; the modern left sidebar currently owns world overview/file discovery and has no Capture category.
- `M2ModelReader` and `M2TrackSampler` already read camera position, target, roll, and modern field-of-view tracks. `M2CameraPathOverlayBuilder` proves sampled camera-only M2 visualization, but no world playback or writer exists.
- The authored project document is required because native M2 has no reliable map/build identity and the viewer's spline intent is richer than a linear sampled track. Native M2 export will therefore be an interoperability artifact with a sidecar.
- The path model already carried position, target, FOV, and roll, but the free camera did not apply roll and the default `System.Text.Json` options serialized `System.Numerics.Vector3` as `{}`. The viewer now owns an explicit path JSON option set with `IncludeFields = true`, and the free camera applies roll around its forward axis. The existing capture queue can consume path keys as still captures, and the existing ffmpeg recorder consumes the continuous path video action.
- Keyboard authoring is opt-in and scoped to the Camera Path workflow: WASD moves, Z/X rolls, K adds the current camera at the playhead, U updates the selected key, Delete removes it, Left/Right selects keys, Ctrl+Left/Right retimes the selected key, Home/End jumps the playhead, Ctrl+Up/Down nudges time, Space toggles playback, Ctrl+S saves JSON, and Ctrl+E exports native M2. Text-entry fields suppress these actions.
- The shared `MdxCameraReader` already decodes classic `CAMS` tracks and `MdxCameraResolver` samples their position, target, roll, visibility, and static FOV data. The viewer should route selected virtual client bytes through those authorities rather than forcing MDX through the standalone M2 adapter.
- Camera-path collision is intentionally bounded for this slice: loaded terrain contributes a heightfield floor, while resident WMO placement bounds provide a conservative exterior swept volume. A path that starts inside a WMO is preserved rather than ejected through its outer AABB; triangle/group collision and collision for evicted content remain follow-up work, so the UI labels WMO collision as conservative and leaves both modes opt-in.
- Native client FlyBy placement is represented by `CinematicCamera.dbc`, whose classic layout exposes `ID`, `Model`, `Origin[3]`, and `OriginFacing`; `CinematicSequences.dbc` carries camera-ID links for sequence playback. The known Undead row (`Cameras\\FlybyUndead.mdx`) has origin `(1658.58, 1662.91, 141.234)` and maps to ADT tile `(28,28)` using the viewer's existing `MapOrigin`/`ChunkSize` projection. Imported M2/MDX keyframes are now marked local until the viewer resolves this row, applies Z-facing plus translation, and stores the resulting world-space path with origin provenance.
