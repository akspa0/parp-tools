## 1. Historical & Technical Context (The 2001 Trailer Bridge)

Between 1999 and 2001, World of Warcraft germinated directly inside a modified version of the **Warcraft III engine** before diverging into the standalone Alpha (`0.5.3`) WDT/ADT engine:
1. **Shared DNA:** Early WoW prototypes (and shots seen in the September 2001 ECTS / E3 trailer) heavily reused or adapted textures from `TerrainArt\` in Warcraft III (specifically *Lordaeron Summer*, *Barrens*, *Ashenvale*, and *Dalaran*).
2. **Fundamental Rendering Shift:**
   - **WC3** uses **discrete corner-bitmasked sub-tiles** packed into `256x256` or `512x256` (and sometimes `512x512` / `1024x512`) `BLP1` texture atlases. Each grid cell on the map draws 1 to 4 overlapping quads based on which terrain types occupy its 4 vertices.
   - **WoW (2001–Alpha 0.5.3)** shifted to **continuous vertex-blended heightmaps (`MCNK`)** using up to 4 seamless repeating textures per chunk (`MCLY`) blended via 64×64 alpha maps (`MCAL`).
3. **The 128×128 vs. 256×256 Anomaly:**
   - In WC3 `BLP1` terrain atlases, a `512x512` (4×4) or `1024x512` (8×4) high-res sheet divides into `128x128` individual sub-tiles (while standard `256x256` / `512x256` sheets divide into `64x64` sub-tiles).
   - When Blizzard migrated WC3 terrain art into early WoW `Tileset\` folders, they extracted the **interior (unmasked) variation sub-tiles** (`128x128` or `64x64`), made them tile seamlessly, upscaled/re-authored them to `256x256`, and converted them from `BLP1` (JPEG/Palettized) to `BLP2` (DXT1/DXT3/Palettized).

## 2. Warcraft II Format Specifications

Warcraft II exists in two primary distributions that `parp-tools` should support:
- **DOS (`Tides of Darkness` / `Beyond the Dark Portal`):** Uses `MAINDAT.WAR` (and `SNDDAT.WAR`, `MUDDAT.CUD`) indexed archives.
- **Battle.net Edition (`W2BN`, 1999):** Uses standard Blizzard `MPQ` v1 archives (`War2Dat.mpq`, `War2Patch.mpq`) containing extracted files with extensions `.cv4`, `.vr4`, `.vx4`, `.ppl`, `.grp`, and `.pud`.

### 2.1 Archive Formats (`MAINDAT.WAR` & `W2BN` MPQ)

If loading from `W2BN`, use your existing MPQ reader with the standard WC2 BNE `(listfile)`. If loading from raw DOS `MAINDAT.WAR`, use the following specification:

#### `MAINDAT.WAR` Header
```c
struct WarArchiveHeader {
    uint32_t magic;          // 0x00000019 (25) or 0x00000018 (24) depending on version
    uint16_t num_entries;    // Total number of resource slots
    uint16_t type;           // 0x0001
    uint32_t offsets[num_entries]; // File offsets from start of archive
};
```

#### `MAINDAT.WAR` Resource Entry & LZSS Decompression
At each `offsets[i]` (ignoring `0x00000000` or `0xFFFFFFFF` empty slots):
```c
struct WarEntryHeader {
    uint32_t flags_and_size; 
    // Uncompressed size = flags_and_size & 0x1FFFFFFF
    // IsCompressed      = (flags_and_size & 0x20000000) != 0
};
```
- **If `IsCompressed == false`:** Read `uncompressed_size` bytes directly behind `WarEntryHeader`.
- **If `IsCompressed == true`:** Decompress until `uncompressed_size` bytes are output using a **4096-byte ring buffer (`uint8_t window[4096]`, initialized to `0`, write cursor `buf_idx = 0`)**:
  1. Read `uint8_t cmd_flags`.
  2. Loop through bits `0..7` of `cmd_flags` (LSB first):
     - **Bit == `1` (Literal):** Read `uint8_t byte`. Write `byte` to output and `window[buf_idx++ & 0xFFF] = byte`.
     - **Bit == `0` (Back-reference):** Read `uint16_t ref` (little-endian):
       - `offset = ref & 0x0FFF` (12-bit absolute index in the 4096-byte ring buffer)
       - `length = (ref >> 12) + 3` (4-bit length + 3, i.e., `3..18` bytes)
       - For `k = 0` to `length - 1`:
         - `b = window[(offset + k) & 0xFFF]`
         - Write `b` to output and `window[buf_idx++ & 0xFFF] = b`.

### 2.2 Color Palettes (`.ppl` / `.pal`)

Every WC2 tileset (`Forest`, `Winter`, `Wasteland`, `Swamp`) has a dedicated 256-color palette (`768 bytes` total):
```c
struct Wc2Color {
    uint8_t r; // 6-bit VGA value (0..63) in DOS/WAR, or 8-bit (0..255) in some BNE dumps
    uint8_t g;
    uint8_t b;
};
```
> **Implementation Note:** Check the maximum byte value across the 768 bytes. If `max_val <= 63`, convert each channel to 8-bit RGB via `(val << 2) | (val >> 4)`. Index `0` is normally transparent for sprites, while indices `208..215` (and `240..254`) are used for water/color cycling and player team colors.

### 2.3 Tileset Graphics Pipeline (`.vr4`, `.vx4`, `.cv4`)

Warcraft II builds `32x32` pixel map tiles ("Megatiles") out of `4x4` grids of `8x8` pixel "Minitiles". Each tileset consists of three companion files:

#### 1. `.vr4` (Minitile Pixel Data)
- Contains raw `8x8` palettized 8-bit pixel blocks (64 bytes per minitile).
- `num_minitiles = file_size / 64`.
- Each byte is a direct lookup into the tileset's `.ppl` palette.

#### 2. `.vx4` (Megatile Definitions)
- Defines how 16 minitiles (`4x4` grid, row-major from top-left to bottom-right) assemble into one `32x32` Megatile.
- Each Megatile entry is `32 bytes` (`16 * uint16_t`):
```c
struct Vx4Megatile {
    uint16_t minitiles[16]; // 4x4 grid of 8x8 minitile references
};
```
- Bitfield breakdown for each `uint16_t entry`:
  - `minitile_index = (entry >> 2) & 0x3FFF` (Index into `.vr4`)
  - `flip_x         = (entry & 0x0001) != 0` (Horizontal mirror of the 8×8 minitile)
  - `flip_y         = (entry & 0x0002) != 0` (Vertical mirror of the 8×8 minitile)

#### 3. `.cv4` (Tile Group / Logical Map ID Lookup)
- Maps logical tile IDs found in `.pud` files to `.vx4` Megatile indices.
- Each `.cv4` record is `52 bytes`:
```c
struct Cv4Entry {
    uint8_t  terrain_flags[20]; // Passability, water, forest, coast flags
    uint16_t megatile_indices[16]; // Variations/sub-indices into the .vx4 table
};
```
- **Direct `.pud` Tile Resolution:** In a `.pud` map's `MTXM` chunk, each cell is a `uint16_t tile_id`. In `W2BN` / `Wargus`, you can either resolve `tile_id` via `cv4[tile_id >> 4].megatile_indices[tile_id & 0x0F]` or, for raw `MTXM` dumps where values directly index `.vx4` in later tools, fall back to direct lookup if `tile_id` maps 1:1. Standard WC2 `.pud` `MTXM` values encode:
  - High nibble/byte (`tile_id >> 4`): Group index in `.cv4`.
  - Low nibble (`tile_id & 0x0F`): Variation index (`0..15`) inside `Cv4Entry.megatile_indices`.

### 2.4 Map Files (`.pud`)

`.pud` files use an IFF-style chunked structure where every section begins with a 4-byte ASCII tag and a Little-Endian `uint32_t length`:

```c
struct PudChunkHeader {
    char     tag[4];   // e.g., "TYPE", "VER ", "ERA ", "DIM ", "MTXM", "UNIT"
    uint32_t length;   // Byte length of payload immediately following
};
```

| Chunk Tag | Size | Payload Specification |
| :--- | :--- | :--- |
| `TYPE` | 16 | `"WAR2 MAP\0\0"` + 6 bytes ID |
| `VER ` | 2 | `uint16_t version` (`0x11` = ToD, `0x13` = BtDP/BNE) |
| `DESC` | 32 | `char description[32]` (Null-terminated ASCII map title) |
| `ERA ` or `ERAX` | 2 | `uint16_t tileset`: `0` = Forest, `1` = Winter, `2` = Wasteland, `3` = Swamp (`ERAX` overrides `ERA ` if present) |
| `DIM ` | 4 | `uint16_t width`, `uint16_t height` (Standard sizes: `32`, `64`, `96`, `128`) |
| `MTXM` | `W * H * 2` | `uint16_t tiles[height][width]` — Row-major grid of `.cv4` tile IDs |
| `UNIT` | `N * 8` | Array of `PudUnit` structs (`x: u16, y: u16, type: u8, owner: u8, arg: u16`) |

### 2.5 Unit & Doodad Sprites (`.grp`)

All WC2 sprites (trees, rocks, units, buildings) use the `.grp` RLE-compressed palettized format:

```c
struct GrpHeader {
    uint16_t frame_count;
    uint16_t max_width;
    uint16_t max_height;
};

struct GrpFrameHeader {
    uint8_t  x_offset;
    uint8_t  y_offset;
    uint8_t  frame_width;
    uint8_t  frame_height;
    uint32_t line_table_offset; // Offset from start of file to uint16_t row_offsets[frame_height]
};
```
**GRP Row RLE Decoding:**
For each row `y` in `0 .. frame_height - 1`:
1. Seek to `line_table_offset + row_offsets[y]`.
2. Set `x = 0`. Loop while `x < frame_width`:
   - Read `uint8_t op`:
   - **If `op >= 0x80` (Skip Transparent):** Advance `x += (op - 0x80)` (leave pixels transparent).
   - **Else if `op >= 0x40` (Run-Length Repeat):** Read `uint8_t color_idx`. Fill the next `(op - 0x40)` pixels with `color_idx`, advancing `x`.
   - **Else (`op < 0x40`, Literal Copy):** Read the next `op` bytes directly as palette indices, advancing `x += op`.

## 3. Warcraft III Format Specifications

Warcraft III spans three major data eras relevant to WoW archaeology:
1. **Alpha/Beta (2001–early 2002):** Uses `.mpq` archives and `BLP0` (external `.b00`–`.b15` mipmaps) or early `BLP1`.
2. **Reign of Chaos (`War3.mpq`, 2002) & The Frozen Throne (`War3x.mpq`, 2003):** Uses `BLP1`, `.slk` tables, `.w3e` v11, and `.mdx` v800.

### 3.1 Archives & Lookup Tables (`.mpq` & `.slk`)

Before loading any WC3 map or tileset, `parp-tools` must parse two Microsoft SYLK (`.slk`) spreadsheet files from `War3.mpq` / `War3x.mpq`:
1. `TerrainArt\Terrain.slk`
2. `TerrainArt\CliffTypes.slk`

#### Minimal SYLK (`.slk`) Parser Algorithm
SYLK files are line-oriented ASCII text files:
- `B;X<cols>;Y<rows>;...` — Defines table bounds (optional to allocate upfront).
- `C;X<col>;Y<row>;K<value>` — Defines cell value at 1-based `(col, row)`. Note that `X` or `Y` may be omitted if unchanged from the previous `C` record!
  - String values in `K` are wrapped in double quotes (e.g., `K"Ldrt"`).
  - Integer/float values in `K` are unquoted (e.g., `K1`).
- Row `Y1` contains the column header names.

#### Key Columns in `TerrainArt\Terrain.slk`
| Column Header | Type | Description |
| :--- | :--- | :--- |
| `tileID` | `char[4]` | 4-character FourCC used in `war3map.w3e` (e.g., `'Ldrt'` = Lordaeron Summer Dirt, `'Lgrs'` = Grass) |
| `dir` | `string` | Directory inside MPQ (e.g., `"TerrainArt\LordaeronSummer"`) |
| `file` | `string` | Base filename without extension (e.g., `"Lords_Dirt"`) → Full path: `{dir}\{file}.blp` |
| `cliffSet` | `int` | Associated cliff index |
| `walkable` / `buildable` | `int` | `1` or `0` pathability flags |

#### Key Columns in `TerrainArt\CliffTypes.slk`
| Column Header | Type | Description |
| :--- | :--- | :--- |
| `cliffID` | `char[4]` | 4-character FourCC (e.g., `'CLdi'`, `'CLgr'`) |
| `cliffModelDir` | `string` | Subdirectory under `Doodads\Terrain\` for cliff `.mdx` meshes (e.g., `"Cliffs"`, `"CityCliffs"`) |
| `rampModelDir` | `string` | Subdirectory under `Doodads\Terrain\` for cliff ramp `.mdx` meshes (`"CliffTrans"`) |
| `texDir` | `string` | Texture folder (e.g., `"ReplaceableTextures\Cliff"`) |
| `texFile` | `string` | Cliff texture filename (e.g., `"Cliff0"`) |
| `groundTile` | `char[4]` | FourCC of base `Terrain.slk` tile forced underneath this cliff |
| `upperTile` | `char[4]` | FourCC of `Terrain.slk` tile forced on top of this cliff (`'_'` if same) |

### 3.2 Texture Format: `BLP0` & `BLP1`

Unlike WoW's `BLP2`, Warcraft III uses **`BLP1`** (and **`BLP0`** in 2001 Beta builds). Critically, **most WC3 terrain textures use `CONTENT_JPEG` (`compression == 0`) with BGRA channel ordering inside a non-standard JFIF stream**, while UI icons and some doodads use `CONTENT_DIRECT` (`compression == 1`, 256-color palettized).

#### `BLP1` Binary Header (`156 bytes` base header)
```c
#pragma pack(push, 1)
struct Blp1Header {
    char     magic[4];         // "BLP1" (or "BLP0" in 2001 beta)
    uint32_t content_type;     // 0 = JPEG compression, 1 = Uncompressed Palettized (Direct)
    uint32_t alpha_bit_depth;  // 0, 1, 4, or 8 (For JPEG: 0 = opaque, 8 = has alpha channel)
    uint32_t width;            // Full mip0 width in pixels
    uint32_t height;           // Full mip0 height in pixels
    uint32_t extra;            // Flags / team color / alpha type (usually 4 or 5)
    uint32_t has_mipmaps;      // 0 = 1 level only, non-zero = mipmaps present
    // Note: In BLP0, the header ends here (28 bytes) and mipmaps are stored in external .b00-.b15 files!
    uint32_t mip_offsets[16];  // File offset from start of BLP1 for each mip level
    uint32_t mip_sizes[16];    // Byte length of each mip level
};
#pragma pack(pop)
```

#### Decoding `content_type == 0` (JPEG BLP1)
Immediately after `Blp1Header` (at offset `0x9C` / `156` in `BLP1`, or offset `0x1C` / `28` in `BLP0`):
```c
uint32_t jpeg_header_size;                 // Typically <= 624 bytes
uint8_t  jpeg_shared_header[jpeg_header_size];
```
To decode Mipmap Level `i` (`0..15` where `mip_offsets[i] != 0 && mip_sizes[i] != 0`):
1. **Concatenate Buffer:** Allocate a buffer of size `jpeg_header_size + mip_sizes[i]`. Copy `jpeg_shared_header` into the start of the buffer, and copy `mip_sizes[i]` bytes from `mip_offsets[i]` immediately after it.
2. **Decode Non-Standard 4-Channel JPEG:**
   - Pass the concatenated buffer to a JPEG decoder (`libjpeg-turbo`, `stb_image`, or custom C# decoder) configured to **not** perform YCbCr→RGB color space conversion!
   - **CRITICAL QUIRK:** Blizzard's JPEG encoder wrote raw **BGRA** planes directly into the 4 JPEG components without YCbCr transformation.
   - Channel mapping from raw decoded JPEG components:
     - Component 0 = **Blue (`B`)**
     - Component 1 = **Green (`G`)**
     - Component 2 = **Red (`R`)**
     - Component 3 = **Alpha (`A`)** (If `alpha_bit_depth == 0`, force `A = 255`).

#### Decoding `content_type == 1` (Palettized BLP1)
Immediately after `Blp1Header` (at offset `0x9C` / `156`):
```c
struct BlpBgrxPalette {
    uint8_t b, g, r, pad; // 256 entries = 1024 bytes total
} palette[256];
```
For Mipmap Level `i` with dimensions `W = max(1, width >> i)` and `H = max(1, height >> i)`:
1. Seek to `mip_offsets[i]`.
2. Read `W * H` bytes of `uint8_t color_indices`.
3. Immediately following `color_indices`, read the alpha buffer based on `alpha_bit_depth`:
   - `alpha_bit_depth == 0`: All pixels have `A = 255`.
   - `alpha_bit_depth == 1`: `(W * H + 7) / 8` bytes. Bit `(pixel_idx % 8)` is `1` (255) or `0` (0).
   - `alpha_bit_depth == 4`: `(W * H + 1) / 2` bytes. 4-bit nibble per pixel (`val * 17`).
   - `alpha_bit_depth == 8`: `W * H` bytes. 1 byte per pixel (`0..255`).

### 3.3 Terrain Atlas Layout & Corner Bitmasking (`4x4` and `8x4`)

Every WC3 terrain `.blp` file is a texture atlas divided into a grid of sub-tiles:
- **Standard Atlas (`width == height`, e.g., `256x256` or `512x512`):** **4 columns × 4 rows** (16 cells, each `1/4` width × `1/4` height).
  - Sub-tile size is `64x64` (for `256x256` BLP) or `128x128` (for `512x512` BLP).
- **Extended Variation Atlas (`width == 2 * height`, e.g., `512x256` or `1024x512`):** **8 columns × 4 rows** (32 cells, each `1/8` width × `1/4` height).
  - Left `4x4` block (Columns `0..3`, Rows `0..3`) = Corner transition tiles + Variation 0.
  - Right `4x4` block (Columns `4..7`, Rows `0..3`) = 16 additional solid interior variations (`Variation 1..16`).

#### Exact Corner Bitmask to Atlas `(Col, Row)` Mapping
When a terrain layer is rendered over a map cell whose 4 vertices have boolean presence `(TL, TR, BL, BR)` for that terrain type (`1` = vertex uses this terrain, `0` = vertex does not), compute the 4-bit mask:
```
mask = (BL ? 1 : 0) | (BR ? 2 : 0) | (TL ? 4 : 0) | (TR ? 8 : 0)
```
The sub-tile `(col, row)` in the left `4x4` block (`0 <= col < 4`, `0 <= row < 4`, with `(0,0)` at top-left) is indexed by:

| `mask` (`0..15`) | Active Corners (`TR TL BR BL`) | Atlas `(Col, Row)` | Description |
| :---: | :---: | :---: | :--- |
| `0` | `0000` | *(Not drawn)* | Layer absent on this cell |
| `1` | `0001` (BL) | `(0, 1)` | Bottom-Left corner only |
| `2` | `0010` (BR) | `(0, 2)` | Bottom-Right corner only |
| `3` | `0011` (BL+BR) | `(0, 3)` | Bottom Half edge |
| `4` | `0100` (TL) | `(1, 0)` | Top-Left corner only |
| `5` | `0101` (BL+TL) | `(1, 1)` | Left Half edge |
| `6` | `0110` (BR+TL) | `(1, 2)` | Diagonal saddle (BR + TL) |
| `7` | `0111` (BL+BR+TL) | `(1, 3)` | Missing Top-Right inner corner |
| `8` | `1000` (TR) | `(2, 0)` | Top-Right corner only |
| `9` | `1001` (BL+TR) | `(2, 1)` | Diagonal saddle (BL + TR) |
| `10` | `1010` (BR+TR) | `(2, 2)` | Right Half edge |
| `11` | `1011` (BL+BR+TR) | `(2, 3)` | Missing Top-Left inner corner |
| `12` | `1100` (TL+TR) | `(3, 0)` | Top Half edge |
| `13` | `1101` (BL+TL+TR) | `(3, 1)` | Missing Bottom-Right inner corner |
| `14` | `1110` (BR+TL+TR) | `(3, 2)` | Missing Bottom-Left inner corner |
| `15` | `1111` (All 4) | `(0, 0)` or `Var 1..17` | **Solid Interior Tile** (No alpha cutout!) |

#### Solid Interior Variations (`mask == 15`)
When all 4 corners of a cell share the base terrain (`mask == 15`), the vertex's 5-bit `ground_variation` (`0..31`) selects which solid tile to draw:
- **In a `4x4` (square) texture:**
  - `variation == 0`: Cell `(0, 0)`
  - `variation == 1`: Cell `(3, 3)` (Note: `(3,3)` in a 4×4 sheet is the secondary solid variation!)
- **In an `8x4` (2:1 wide) texture:**
  - `variation == 0`: Cell `(0, 0)`
  - `variation == 1`: Cell `(3, 3)`
  - `variation == 2..17`: Right-hand `4x4` block, where `idx = variation - 2`:
    - `col = 4 + (idx / 4)`
    - `row = idx % 4`

> **UV Inset Warning (Preventing Mipmap Bleed):** Because WC3 packs 16 or 32 discontinuous sub-tiles into a single texture without padding gutters, bilinear filtering will bleed across sub-tile borders unless you clamp/inset UVs by half a texel (`0.5 / tex_width`, `0.5 / tex_height`) or load each sub-tile into a `GL_TEXTURE_2D_ARRAY` layer with `GL_CLAMP_TO_EDGE`.

### 3.4 Environment / Terrain Mesh (`war3map.w3e`)

`war3map.w3e` defines the heightmap, tileset palette, cliff layers, and vertex data.

#### Header Structure
```c
struct W3eHeader {
    char     magic[4];              // "W3E!"
    uint32_t version;               // Always 11 (0x0B) for RoC/TFT
    char     main_tileset;          // e.g. 'L' (Lordaeron Summer), 'A' (Ashenvale), 'B' (Barrens)
    uint32_t is_custom_tileset;     // 0 = default, 1 = custom
    uint32_t num_ground_tilesets;   // Max 16
    char     ground_tilesets[num_ground_tilesets][4]; // FourCCs referencing Terrain.slk
    uint32_t num_cliff_tilesets;    // Max 16
    char     cliff_tilesets[num_cliff_tilesets][4];   // FourCCs referencing CliffTypes.slk
    uint32_t map_width_plus_one;    // Number of vertex columns (Mx = width + 1)
    uint32_t map_height_plus_one;   // Number of vertex rows    (My = height + 1)
    float    center_offset_x;       // World X coordinate of bottom-left corner (usually -64 * width)
    float    center_offset_y;       // World Y coordinate of bottom-left corner (usually -64 * height)
};
```

#### Vertex / Tilepoint Record (`7 bytes` per corner)
Immediately following `W3eHeader` are `Mx * My` 7-byte records ordered **bottom-to-top (`y = 0 .. My-1`), left-to-right (`x = 0 .. Mx-1`)**:

```c
#pragma pack(push, 1)
struct W3eTilepoint {
    uint16_t ground_height;          // 14-bit value (0x2000 = 8192 = zero level)
    uint16_t water_and_edge;         // Bits 0..13: water height; Bit 14: boundary flag 1; Bit 15: boundary/camera edge
    uint8_t  flags_and_ground_type;  // Bits 0..3: ground_tilesets index (0..15);
                                     // Bit 4 (0x10): ramp; Bit 5 (0x20): blight; Bit 6 (0x40): water; Bit 7 (0x80): boundary2
    uint8_t  variation;              // Bits 0..4: ground_variation (0..31); Bits 5..7: cliff_variation (0..7)
    uint8_t  cliff_and_layer;        // Bits 0..3: layer_height (0..15, where 2 = base ground level);
                                     // Bits 4..7: cliff_tilesets index (0..15)
};
#pragma pack(pop)
```

#### World-Space Coordinate & Elevation Math
Every WC3 terrain cell is **128.0 × 128.0 world units** (`4.096` yards in WoW scale, or `1/3` of a WoW `MCNK` chunk width). For vertex `(x, y)`:
```c
float world_x = center_offset_x + (x * 128.0f);
float world_y = center_offset_y + (y * 128.0f);

int   layer_height = cliff_and_layer & 0x0F;
float base_z       = ((int)(ground_height & 0x3FFF) - 8192) / 4.0f;
float final_z      = base_z + ((layer_height - 2) * 128.0f);

float water_z      = (((int)(water_and_edge & 0x3FFF) - 8192) / 4.0f) - 89.6f;
```

#### Cell Layer Rendering Order
For each grid quad `(x, y)` formed by corners `BL=(x,y)`, `BR=(x+1,y)`, `TL=(x,y+1)`, `TR=(x+1,y+1)`:
1. **Check Cliff / Ramp Status:** If the four corners do not all share the same `layer_height` (and are not flagged as a smooth ramp), the cell is a **3D Cliff Mesh** rather than a simple terrain quad. Look up the cliff `.mdx` model via `CliffTypes.slk` using the relative height differences `(TL_layer, TR_layer, BL_layer, BR_layer)` (e.g., `CliffsBABA0.mdx`).
2. **Collect Ground Texture Indices:** Gather the up to 4 `ground_type` indices from `{BL, BR, TL, TR}`.
   - If any vertex has `blight` (`flags & 0x20`), substitute the Blight texture index at its priority slot.
3. **Sort Ascending:** Sort unique texture indices on the cell in ascending order (`t_0 < t_1 < ... < t_k`).
4. **Draw Layered Quads:**
   - **Pass 0 (`t_0`, lowest index):** Always force `mask = 15` (solid interior tile, using `BL.ground_variation`) so the cell has a completely opaque base layer.
   - **Pass `1..k` (`t_i`):** Compute the 4-bit corner `mask` (`1..14`) for all corners where `corner.ground_type == t_i`, look up the `(col, row)` sub-tile in texture `t_i`, and alpha-blend it on top of Pass 0.

### 3.5 3D Models (`.mdx`) & Map Placements (`.doo`)

#### `.mdx` Model Format Overview (Version 800)
WC3 `.mdx` is the direct ancestor of WoW's `.m2` (and almost identical to the `.mdx` format used in WoW 0.5.3 Alpha before the `.m2` conversion!).
- Starts with 4-byte magic `"MDLX"`.
- Followed by tagged chunks: `char tag[4]; uint32_t byte_size;`
  - `VERS`: `uint32_t version` (`800` for RoC/TFT; WoW 0.5.3 Alpha `.mdx` uses `1300`–`1500`).
  - `MODL`: `char name[80]`, `char anim_file[260]`, `Extent bounds`, `uint32_t blend_time`.
  - `TEXS`: Array of `268-byte` texture records (`uint32_t replaceable_id; char file_name[260]; uint32_t flags;`).
    - **Note for Cliff Models:** `replaceable_id == 11` (`0x0B`) or `ReplaceableTextures\Cliff\Cliff0.blp` must be dynamically swapped with the map's cliff texture from `CliffTypes.slk`!
  - `MTLS`: Materials and shader layers (`LAYS`).
  - `GEOS`: Geosets containing sub-chunks `VRTX` (`float[3]` positions), `NRMS` (`float[3]` normals), `UVBS` (`float[2]` UVs), `PTYP`, `PCNT`, `PVTX` (`uint16_t` triangle indices), `GNDX` (vertex group indices), `MTGC`, `MATS`.

#### Doodad Placement File (`war3map.doo`)
Places trees, rocks, and props onto the `.w3e` terrain:
```c
struct DooHeader {
    char     magic[4];      // "W3do"
    uint32_t version;       // 7 (RoC) or 8 (TFT)
    uint32_t subversion;    // 0x09 (v7) or 0x0B (v8)
    uint32_t num_doodads;
};

struct DooEntryV8 {
    char     type_id[4];    // FourCC in Doodads\Doodads.slk or Units\DestructableData.slk
    uint32_t variation;
    float    pos[3];        // World (X, Y, Z) matching .w3e world space
    float    angle;         // Radians around Z axis
    float    scale[3];      // (scaleX, scaleY, scaleZ)
    uint8_t  flags;         // 0=invisible/non-solid, 1=visible/non-solid, 2=normal
    uint8_t  life;          // Percentage (0..100)
    uint32_t item_table_ptr;// (Present in v8 only; followed by item set count)
    uint32_t creation_num;  // Unique ID
};
```

## 4. Restoration Pipeline: WC3 to WoW 2001 / Alpha (`0.5.3`)

To test whether WC3 tilesets match the **2001 WoW Trailer** and restore them into WoW Alpha WDT/ADT maps (`0.5.3`–`0.5.5`), `parp-tools` needs an automated conversion pipeline that transforms WC3 `TerrainArt\*\*.blp` atlases into WoW `Tileset\*\*.blp` (`BLP2`) textures.

### 4.1 De-Atlasing WC3 Tilesets to Seamless WoW Alpha `MTEX` Tiles

Why you **cannot** feed a raw WC3 terrain `.blp` directly into a WoW ADT `MTEX` slot:
1. A WC3 terrain `.blp` is an **atlas** of 16 (`4x4`) or 32 (`8x4`) sub-tiles where 14 of the sub-tiles contain alpha-masked rounded corners (`mask 1..14`).
2. WoW's `MCNK` terrain chunk expects a **single, fully opaque, seamlessly repeating `256x256` texture** (with the optional specular mask in the alpha channel) and performs transitions via vertex/chunk `MCAL` alpha maps.

#### Extraction Algorithm for `parp-tools`
Given a decoded WC3 terrain `BLP1` image of dimensions `(W, H)`:
1. Determine grid dimensions:
   - `cols = (W == H * 2) ? 8 : 4`
   - `rows = 4`
   - `sub_w = W / cols` (Typically `64` or `128`)
   - `sub_h = H / rows` (Typically `64` or `128`)
2. Extract the **Solid Interior Sub-Tiles (`mask == 15`)**:
   - **Primary Base Tile (`Var 0`):** Crop rectangle `(0, 0, sub_w, sub_h)` (Cell `0,0`).
   - **Secondary Base Tile (`Var 1`):** Crop rectangle `(3 * sub_w, 3 * sub_h, sub_w, sub_h)` (Cell `3,3`).
   - **Extended Variations (`Var 2..17`, if `cols == 8`):** Crop all 16 cells in Columns `4..7`, Rows `0..3`.

---

### 4.2 Resampling Pipeline (`64x64` / `128x128` → `256x256`)

When converting extracted `64x64` or `128x128` WC3 sub-tiles into `256x256` WoW Alpha `BLP2` textures, `parp-tools` should support three selectable modes in the viewer to compare against 2001 trailer footage:

1. **Mode A: `2x2` Tiled Composite (`128x128` → `256x256` Multi-Variation Composite)**
   - For `8x4` WC3 tilesets with `128x128` cells (or `64x64` upscaled `2x` to `128x128`), assemble four distinct interior variations (`Var 0`, `Var 1`, `Var 2`, `Var 3`) into a `2x2` grid (`256x256`).
   - *Historical Note:* Early Blizzard artists frequently combined 4 variations of a WC3 `64x64`/`128x128` tile into a single `256x256` WoW texture to break up repetition before painting over the inner seams!
2. **Mode B: Toroidal (Wrap-Around) Lanczos-3 Upscale (`128x128` → `256x256`)**
   - Upscale a single `128x128` interior cell (e.g., `Cell(0,0)`) to `256x256`.
   - **Crucial:** The resampler **must wrap pixel coordinates toroidally** (`x % sub_w`, `y % sub_h`) at the borders during convolution! Standard clamped bilinear/bicubic upscaling creates a visible 1–2 pixel seam along the edges when tiled across an `MCNK` chunk.
3. **Mode C: Integer Nearest-Neighbor + Box/Gaussian Pass**
   - Preserves crisp 2001-era texel structure without ringing artifacts.

---

### 4.3 `BLP1` to `BLP2` Binary Transcoder Specification

Once the `256x256` RGBA8 buffer is prepared, generate a full **9-level Mipmap Chain** (`256x256` down to `1x1`, using toroidal wrap-around box/Kaiser downsampling) and serialize to **`BLP2`**:

#### `BLP2` Binary Header (`148 bytes` + `1024-byte` Palette = `1172 bytes` / `0x494`)
```c
#pragma pack(push, 1)
struct Blp2Header {
    char     magic[4];           // "BLP2"
    uint32_t version;            // Always 1
    uint8_t  color_encoding;     // 1 = Palettized, 2 = DXTC (BC1/BC2/BC3), 3 = Uncompressed BGRA
    uint8_t  alpha_bit_depth;    // 0, 1, 4, or 8 (For WoW terrain: 0 for non-specular, 8 for specular mask)
    uint8_t  alpha_encoding;     // 0 = DXT1, 1 = DXT3, 7 = DXT5 (or 8 for palettized)
    uint8_t  has_mips;           // 1 = Mipmaps present
    uint32_t width;              // 256
    uint32_t height;             // 256
    uint32_t mip_offsets[16];    // File offsets for mip levels 0..8 (9..15 = 0)
    uint32_t mip_sizes[16];      // Byte sizes for mip levels 0..8   (9..15 = 0)
    uint32_t palette[256];       // 1024 bytes (Zero-filled if color_encoding == 2 DXTC)
};
#pragma pack(pop)
```

#### Target Encoding Recommendations for WoW Alpha (`0.5.3`–`0.5.5`):
- **Option 1 (DXT1 / BC1 — Standard Alpha Terrain):**
  - `color_encoding = 2`, `alpha_bit_depth = 0`, `alpha_encoding = 0`, `has_mips = 1`.
  - Mip `i` byte size = `max(1, (W_i + 3) / 4) * max(1, (H_i + 3) / 4) * 8`.
- **Option 2 (Palettized 8-bit + 8-bit Specular Alpha — Used by several 0.5.3 Tilesets):**
  - `color_encoding = 1`, `alpha_bit_depth = 8`, `alpha_encoding = 8`, `has_mips = 1`.
  - Quantize all mip levels against a shared 256-color Wu/NeuQuant BGRX palette stored in `header.palette`.
  - Mip `i` byte size = `(W_i * H_i) + (W_i * H_i)` (Indices followed by 8-bit alpha specular values).
