# parp-tools WoW Viewer v0.5.2.1

A patch release, out of band, for one reason: **v0.5.2 shipped with a frame-pacing bug that made
movement jank badly, and it took building a proper detector to find out why.** The cause was not
where anyone assumed.

This is a fix release, not a feature release. Nothing about what the viewer *renders* changed.

## Why this is a sudden patch

v0.5.2's renderer "galloped" — jagged frame pacing, periodic hitches, worst while moving across ADT
tile boundaries. It was known and unresolved at release. The investigation that followed found the
existing profiler could not see the defect at all: it sampled a **stationary** camera for 12 frames
and reported no frame-time distribution, so every "no hitch found" result it had ever produced was a
false negative.

Once a detector existed that could see it, the cause turned out to be four separate defects, and the
leading theory going in — per-frame allocation churn in the scene graph — was **refuted by
measurement**. Median world-render CPU is 0.33–8.58 ms; a renderer with a sub-millisecond median does
not have an allocation-throughput problem.

## What was actually wrong

**A periodic ~283 ms stall, four times a second, in a pass with no timer.** `WorldFramePasses`
declared eleven passes and ten of them recorded a stage timer. The eleventh, `PrepareObjectPhase`,
recorded none — so its entire cost was invisible to the stage table *by construction*, and the stall
sat in unaccounted time for the whole investigation.

Its cost was not rendering, and not audio playback. It was the audio **emitter diagnostics panel**
rebuilding a record for every resident sound emitter — 5,565 of them in a dense zone — on the render
thread, on a 250 ms timer, **whether or not anything was displaying the result**. A second copy ran
synchronously whenever streaming evicted a tile, which is precisely when you are moving.

**Every opaque MDX drew one draw call per instance.** WMO batching worked; MDX batching was
completely inert. The cause was a route planner whose entire predicate body was `return true`,
sending 100% of instances down the per-instance fallback while the batching machinery sat unused.

**The deferred asset loader checked its frame budget only between loads,** so once a load started it
ran to completion — 58 ms against a 3.5 ms budget.

**Audio range was evaluated against every streamed tile,** with no reference to which tile the camera
was actually on.

## Fixes

- **Audio diagnostics no longer run unless something is displaying them**, and tile eviction no longer
  rebuilds them synchronously. `PrepareObjectPhase` max fell from **283.4 ms to 2.5 ms** and stopped
  appearing in the hitch list.
- **Opaque MDX batching restored.** From **0 batched / 312 unbatched** to **526 batched / 3
  unbatched**; `MdxOpaqueSubmission` p99 fell **30.75 → 14.12 ms** and median **2.03 → 0.01 ms**. The
  remaining unbatched instances are models that genuinely cannot batch, and they are counted.
- **`PrepareObjectPhase` now has a stage timer**, and a test now fails the build if any frame pass is
  added without one. Unaccounted frame time fell from a 259–314 ms pass gap to **median 0.02 ms /
  p99 0.11 ms**.
- **Deferred loads are admitted against a learned per-asset cost estimate** before starting, instead
  of only between loads.
- **Audio is scoped to the camera's tile and its immediate ring**, using the terrain manager's own
  camera tile rather than re-deriving it.

## Known issues — read this before reporting

**Dense WMO interiors are still slow, and Stormwind is the worst case.** Entering the city submits
**all districts at once** — 7,512 visible groups and 80,484 draw calls — instead of only the district
group the camera is inside. This is a WMO group *admission* problem, not a batching one (80,200 of
those 80,484 calls are correctly batched). Portal-aware admission exists, but it is not constraining
a city-sized multi-group interior, and the client almost certainly uses group-to-group visibility
data that this renderer does not yet read.

This is **not fixed in this release** and is the next thing being worked on. If you fly into
Stormwind and the framerate collapses, that is this bug, and it is already known.

Also still open:

- Deferred asset loading can spike to ~443 ms on a single load in a dense zone. The budget now bounds
  the *additive* overshoot, but a single synchronous decode still costs what it costs — moving decode
  off the render thread is the real fix and is not done.
- Sound emitters decoded from `MCSE` read as permanently out of range; only water-triggered emitters
  behave. The position transform assumes a chunk-local coordinate frame on the strength of a code
  comment with no evidence behind it. Rather than guess, this release adds a **measurement** —
  Utilities > Audio now reports what frame the positions are actually in — so the fix can be written
  against data instead of a hunch.

## Honest scope

Every performance number above was measured before and after on the same route and machine.
Absolute timings are machine-specific; the comparisons are what matter. Nothing here has been
credited with fixing something it did not fix — in particular, restoring MDX batching did **not**
remove the hitching, and is not claimed to have.
