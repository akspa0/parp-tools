# Advanced V16 Workflows

This is the detailed companion doc for `data-harvester/README.md`.

## Dataset commands

### Build

```powershell
uv run python scripts/build_v16_dataset.py build --build 3_3_5_12340
uv run python scripts/build_v16_dataset.py build --build 3_3_5_12340 --resume
uv run python scripts/build_v16_dataset.py build --build 3_3_5_12340 --rebuild-existing
```

Useful options:
- `--codec {none,lz4,zstd}` (default `lz4`)
- `--clevel <int>`
- `--shuffle {noshuffle,shuffle,bitshuffle}`
- `--signal-validation/--no-signal-validation`
- `--signal-validation-strict/--no-signal-validation-strict`

Current default profile:
- `--codec lz4`
- `--clevel 1`
- `--shuffle shuffle`

### Patch liquids in-place

```powershell
uv run python scripts/build_v16_dataset.py patch-liquids --build 0_5_3_3368
uv run python scripts/build_v16_dataset.py patch-liquids --builds 0_5_3_3368 0_5_5_3494 0_7_0_3694 3_0_1_8303 3_3_5_12340 4_0_0_11927
```

Notes:
- Rewrites only `liquid_mask`, `liquid_height`, and liquid `has_*` flags in `index.parquet`.
- Creates `index.parquet.bak.liquids` unless `--no-backup`.
- Writes `liquid_patch_report.json`.

```powershell
uv run python scripts/build_v16_dataset.py validate-signals --build 3_3_5_12340
uv run python scripts/build_v16_dataset.py validate-signals --builds 0_5_3_3368 0_5_5_3494 0_7_0_3694 3_0_1_8303 3_3_5_12340 4_0_0_11927
```

## Renderer-Truth Capture Pipeline (V16.2)

### Overview

The V16.2 dataset adds two renderer-truth signals that the harvest stream
cannot produce: `object_visibility_mask` and `no_object_minimap`. These are
generated by MdxViewer rendering the game client and differencing capture
families.

**What the harvest stream produces** (all core terrain signals):
height, normals, alpha, holes, liquid, object masks, minimap RGB, shadow,
MCLY/MCAL, placements.

**What the viewer captures** (renderer-truth overlay):
object visibility mask (primary vs noobjects diff), terrain-only minimap.

### Step 1: Generate per-tile stubs

```powershell
cd i:\parp\parp-tools\wow-viewer\data-harvester
uv run python scripts/build_v16_dataset.py generate-viewer-stubs `
  --builds 0_5_3_3368 0_5_5_3494 0_7_0_3694 3_0_1_8303 3_3_5_12340 4_0_0_11927
```

This reads `index.parquet` from each V16 Zarr store and writes minimal
per-tile JSON stubs into `output/tmp/mdxviewer_validation_smoke/<build>/dataset/`.
The filenames follow the format `MapName_tileY_tileX.json` which the
viewer's `TryParseMkDatasetTileCoordinates` parser expects.

### Step 2: Run MdxViewer capture batches

```powershell
scripts\generate_all_renderer_truth_captures.bat
```

Each viewer session requires:
- `--game-path` — staged client root
- `--build` — build version string (e.g. `3.3.5.12340`)
- `--listfile` — community listfile for name resolution
- `--world` — WDT path for the map (e.g. `World\Maps\Azeroth\Azeroth.wdt`)
- `--validation-dataset-root` — directory with `dataset/` subdirectory
- `--validation-output` — where to write PNGs
- `--validation-resolution` — capture size (256-4096)
- `--force-validation-regeneration` — re-capture existing
- `--exit-after-validation` — close when done

Per build, the viewer renders 4 families:
- **primary** — terrain + liquids + WMOs + doodads
- **noliquids** — terrain + objects (liquids hidden)
- **noobjects** — terrain + liquids only (objects hidden)
- **objectsonly** — WMOs only (terrain/liquids/sky hidden)

After capture, `GenerateMkHarvestViewerValidationObjectArtifacts` produces:
- `images/<tile>_object_visibility_mask.png` — diff of primary vs noobjects
- `images/<tile>_no_objects.png` — copy of noobjects capture

### Step 3: Patch into Zarr stores

```powershell
uv run python scripts/build_v16_dataset.py patch-renderer-truth `
  --builds 0_5_3_3368 0_5_5_3494 0_7_0_3694 3_0_1_8303 3_3_5_12340 4_0_0_11927
```

This reads the captured PNGs and writes `object_visibility_mask` (float32)
and `no_object_minimap` (uint8 RGB) arrays into the V16 Zarr stores.

### Future: Zarr-native viewer

The eventual goal is for the wow-viewer to read terrain geometry directly
from V16 Zarr stores instead of game client archives. The Zarr stores are
compact and fast compared to MPQ, and already contain all terrain, texture,
and object signals from the harvest. The viewer would only need the game
client for rendering (shaders, models, textures) while loading terrain
geometry from the store.
